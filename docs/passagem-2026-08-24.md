## 4. Como a frente do Pix volta a andar

As duas frentes se tocam num ponto só, o grafo de migrações. Ficou resolvido
assim:

- `0060_blog` sai da `0058`, para o blog não depender do Pix. Está na `main`.
- `0061` (do Pix) passou a declarar que depende **da `0059` e da `0060_blog`**.
  A `0059` cria a tabela `PixCharge` que a `0061` altera; a dependência era
  implícita enquanto a cadeia era linear, e deixou de ser.

**Essa correção da `0061` está na árvore deste computador e não está commitada.**
Comitte antes de qualquer outra coisa:

```bash
git add core/migrations/0061_pixcharge_public_token_and_more.py
git commit -m "fix: 0061 depende tambem da 0059, que cria a PixCharge"
```

Depois, para a branch do Pix absorver o blog que já está na `main`:

```bash
# 1. confira que não há trabalho seu não commitado nestes ficheiros
git diff --stat core/models.py core/admin.py core/urls.py

# 2. descarte a cópia do blog que está solta na árvore; ela agora vive na main
git checkout -- core/models.py core/admin.py core/urls.py \
                frontend/templates/landing_v8.html frontend/templates/legal_base.html

# 3. traga o blog
git merge main
```

Se o passo 3 reclamar de ficheiros não rastreados que seriam sobrescritos,
apague as cópias soltas do blog (`core/blog_*.py`, `core/templatetags/`,
`core/tests_blog.py`, `core/migrations/0060_blog.py`,
`core/management/commands/blog_*.py`, `frontend/templates/blog/`,
`docs/blog.md`) e repita o merge: as versões boas vêm da `main`.

Depois do merge, confirme que o grafo ficou com uma folha só:

```bash
.venv/Scripts/python.exe dev_local.py showmigrations core | tail -6
DB_NAME=cini_blogtest .venv/Scripts/python.exe dev_local.py test core --noinput
```

## 5. Ambiente local, do zero, no outro computador

```bash
git clone https://github.com/jonasbarros98/cini-english.git
cd cini-english
py -3.12 -m venv .venv
.venv/Scripts/python.exe -m pip install -r requirements.txt
```

Falta o `.env`, que **não está no repositório de propósito** (ele foi retirado
em 13/08 porque tinha segredos reais num repositório público). Copie o do
computador antigo, ou monte a partir do `.env.example`.

Precisa também de Postgres 17 local com uma base `cini_english`.

**Rode sempre pelo `dev_local.py`, nunca pelo `manage.py`:** ele desliga o envio
real de e-mail e o webhook do n8n. Rodar `manage.py` na sua máquina manda e-mail
de verdade para usuário real.

```bash
.venv/Scripts/python.exe dev_local.py migrate
.venv/Scripts/python.exe dev_local.py runserver 8000 --insecure
```

Para rodar os testes sem esbarrar noutra sessão que esteja a usar a base de
teste, use um nome próprio:

```bash
DB_NAME=cini_blogtest .venv/Scripts/python.exe dev_local.py test core --noinput
```

## 6. Deploy, em três linhas

Merge com `--no-ff` na `main` mais push, e o Railway constrói sozinho pelo
Dockerfile. Ambiente correto no Railway: **`cini-english`** (o chamado
`production` está abandonado e engana).

```bash
git checkout main && git merge --no-ff <branch> -m "Merge: ..."
git push origin main
```

**Uma coisa aprendida hoje, que vale guardar:** o `preDeployCommand` do
`railway.json` **não executou**. A migração aplicou e o site subiu, mas o comando
de semear o blog nunca correu. O que roda de facto é o `CMD` do `Dockerfile`. Se
precisar que algo aconteça a cada arranque, é lá, e sempre num segmento próprio
terminado em `|| true`, para nunca impedir o gunicorn de arrancar.

**Voltar atrás com o blog**, se algum dia for preciso:

```bash
git revert -m 1 a46b808
git revert -m 1 b70efe4
git push origin main
```

Ou, mais rápido, Railway > Deployments > HISTORY > deploy anterior > Redeploy.
